# 「爱看电视」全原生客户端可行性研究

- 研究时间：2026-11-04
- 研究对象：现 v2.6.4（WebView 套壳 + tv.js/tv.css 注入 + 原生 PlayerActivity）→ 全原生 Android TV 客户端
- 证据基线：`site-probe-report.md`（2026-11-03 官网只读探测，19 次 GET）、现有工程源码全量阅读、站点页面源码副本（home/search/play.html、play_new.js），以及 2026-11-04 上午 2 次 live GET 复验（首页 HTTP 200、27078 字节与昨日副本**逐字节同尺寸**；播放页 200、隐藏字段齐全、无 Cloudflare 校验）

---

## 结论（先行）

**推荐：混合渐进原生化，不推倒重来，也不长期停在纯套壳。**

三条理由：

1. **这个 App 其实已经原生了一大半。** 播放器（libVLC、选集/换源面板、线路测速、坏源自动换线、倍速、续播）是 100% 原生代码（PlayerActivity 988 行）；播放取数也是原生优先——`fetchLinesNative` 用两次普通 HTTPS 请求 + 已逆向的 token 算法直取全部线路，WebView harvest 只是回退。真正还绑在 WebView 上的只剩**浏览层**（首页/分类/搜索/榜单/看过）一份工作。
2. **浏览层的数据全是规整的服务端渲染 HTML，只有两套卡片模板**，字段映射简单、跨日字节级稳定（见 §1）。解析风险远低于现在注入层与站点 JS/CSS 互相打架的风险——v2.6 的「`.row .item` 宽度误伤锚点、海报整列压成细条」事故就是注入方案的典型死法，原生 UI 不存在这类问题。
3. **原生 HTTP 客户端直达站点已被真机证明，不是假设**：v2.6.4 的 fetchLinesNative 用的就是 HttpURLConnection + 桌面 UA，已在盒子上跑通；探测用的 curl（非浏览器 TLS 指纹）全站路径也全部 200。Cloudflare 风险可控，但必须保留 WebView harvest 作为兜底通道（见 §4）。

预计总工作量 **约 5–8 个开发日**（按此前单日多版的迭代节奏折算），分三阶段，每阶段结束都可独立发版（见 §6）。

## 1. 数据来源映射：每个界面吃什么

站点没有浏览类 API（全站只有一个 XHR 接口 `/api/getResN`）。原生化 = **接口的归接口（播放），页面的归解析（浏览）**。好消息是页面结构高度模板化，全站只有两套条目模板。

### 1.1 两套条目模板（解析器只需写两个）

**模板 A：网格卡**（首页、/hot/ 列表、/category/、/billboard/ 全用它）

```html
<div class="col-xs-4 col-sm-3 col-md-2 item">
  <a class="item" href="/play/{videoId}">
    <div class="embed-responsive cover-wp">
      <img class="lazy" id="{videoId}" alt="{标题}"
           data-src="{豆瓣原图URL}" src="data:image/svg…"/>
    </div>
    <p>{标题}</p>
  </a>
</div>
```

| 字段 | 来源 | 备注 |
|---|---|---|
| videoId | `a.item` 的 href `/play/(\d+)`，或 `img@id`（两者一致，互为校验） | 点播时直接拼 `/play/{videoId}` 交给 PlayerActivity |
| 标题 | `a.item > p` 文本（与 `img@alt` 相同） | |
| 海报原图 | `img@data-src`（`src` 是占位 SVG，忽略） | |
| 海报最终 URL | 按已摸清的站点规则本地拼装：doubanio 图 → `https://imgp.ikanbot.eu.org/i/{videoId}?u={base64url(原图)}`，失败回退 imgp1/imgp2 → `/proxy?url=` → 原图直连；非豆瓣图直连 | 此规则现已在 tv.js 的 `loadPosters()` 里实现，原生侧照搬即可（约 20 行） |
| 板块归属 | 所属 `.v-list` 容器的 `h4` 文本（板块名）+ `h4 span a@href`（「更多」目标） | 首页板块顺序、名称全部数据驱动，不用硬编码 |

**模板 B：搜索列表卡**（/search 专用，Bootstrap media 结构）

```html
<div class="media">
  <div class="media-left"><a class="cover-link" href="/play/{videoId}">
    <img class="media-pic lazy" id="{videoId}" alt="{标题}" data-src="{原图}"/></a></div>
  <div class="media-body"><h5 class="media-heading">…</h5>…简介/演职员文本…</div>
</div>
```

字段映射与模板 A 等价（videoId/标题/海报同规则），多一段 media-body 的描述文本可作副标题。解析器为搜索页单独写一个选择器集即可，约多 30 行。

### 1.2 逐界面数据表

| 界面 | URL | 取数方式 | 分页 | 说明 |
|---|---|---|---|---|
| 首页 | `GET /`（27KB） | 解析模板 A，按 `.v-list` 分组（现 3 板块：最近热门电影/剧集/一周口碑榜） | 无 | 一次请求拿全首页；板块与「更多」链接都从 h4 提取 |
| 电影/剧集列表 | `/hot/index-{movie\|tv}-{标签}.html`，翻页追加 `-p-{n}` | 解析模板 A（24 条/页） | **页码式、可构造** | 标签清单（热门/华语/动作/国产剧/韩剧…）从首页导航或板块「更多」链接提取后内置，站点加标签时列表页内也有全集链接可再提取 |
| 分类 | `/category/`（最新入库）、`/category/{1=电影,2=剧集,18=动漫,19=综艺,20=纪录片}` | 解析模板 A（48 条/页样本） | **查询参数式 `?p={n}`、可构造**（与 /hot/ 的路径式不同，解析器各写一个 URL 拼法） | 与 /hot/ 高度重叠，可作二期或直接不做（现 App 底部栏也没有分类入口，是站点隐藏项） |
| 榜单 | `/billboard.html`（79KB，单页） | 解析模板 A，按榜单标题分段（条目带名次） | 无 | 多个榜单拼在一页，按 h 标题切分；共约 90 个条目 |
| 搜索 | `/search?q={词}`（20 条/页） | 解析模板 B | **游标式、不可构造**：第 2 页起须从当前页 HTML 里提取带 `n=` 的下一页链接原样跟随（n 是搜索引擎的 search-after 游标） | 解析器须实现「提取页内下一页 href」而非拼 URL；搜索无建议/联想接口，输入法交互与现方案相同 |
| 片单（可选） | `/kanlist/{主题}-p-{n}.html` → `/article/{id}` | 解析 article 页内的模板 A 链接（约 20 个/篇） | 页码式 | 这是站点的编辑内容（主题片单文章），现 App 未突出此入口；原生化时可放二期或舍弃 |
| 看过/历史 | **本地生成**（见 §3） | 不请求站点 | — | 站点 /history.html 本来就是纯前端读 localStorage，原生侧自己存自己渲染，天然脱钩 |
| 播放（详情+线路） | `GET /play/{videoId}` HTML + `GET /api/getResN` | **现成**：fetchLinesNative 已实现——正则提取隐藏字段 `current_id`/`e_token`/`mtype` + `#video_title` 元素文本 → 直算 token → getResN 拿全部「线路×集数」 | — | 播放页静态 HTML 里没有集数（集数全在 getResN 响应里），所以原生播放不需要再解析任何播放页 DOM |

### 1.3 解析的稳定性与脆弱点

**稳定的依据**：
- 站点是成熟模板站（Bootstrap 3 + 服务端渲染），本次复验首页与昨日副本同为 27078 字节，探测期 home.html 与 home-desktop.html 亦逐字节一致。
- HTML 走 CDN 边缘缓存 1 小时，内容本身就是慢变量。
- 字段都有强锚点：videoId 是纯数字路径、隐藏字段是 id 属性、卡片是固定 class 组合，不依赖易变的文案或位置序号。

**脆弱点（按风险排序）**：
1. **token 算法**（播放，两方案共同风险）：写在页面内联混淆脚本里、无版本号，站点可随时改。已有对策：原生直算失败/state=-401 → 回退 WebView harvest（v_tks 由页面 JS 现算）。原生化后这条回退链必须保留（见 §4、§6 阶段三）。
2. **class 名改版**：站点若重构前端模板，模板 A/B 的选择器会失效。对策：解析器集中在一个类里、选择器常量化；且解析出 0 条目时自动降级到「原站模式」（保留的 WebView 入口），用户不至于没得看，修复只需改选择器发小版。
3. **搜索游标**：`n` 不可构造，若站点改搜索实现，翻页逻辑要跟着改；第 1 页永远可达，影响面仅限翻页。
4. **标签/分类体系调整**：/hot/ 标签是中文词直入 URL，站点增删标签时内置清单会漂移；影响小（主流标签多年稳定），且可从页面导航动态提取兜底。
5. **海报代理域名**：imgp.ikanbot.eu.org 及其回退链是站点自有基础设施，域名/规则变更时海报会回退到豆瓣直连（功能不中断，速度变差）。

## 2. 复用盘点：播放器与取数层几乎全留

现有工程共约 1940 行（Java 1474 + tv.js 273 + tv.css 196）：

| 资产 | 行数 | 原生化后命运 |
|---|---|---|
| PlayerActivity：libVLC 播放、VLCVideoLayout 缩放、选集/换源双面板、线路测速、坏源自动换线、倍速、OSD、续播存取 | ≈840 | **原样复用**。它与浏览层之间只有一个入参（`EXTRA_URL` = /play/ 链接字符串），原生列表页拼出同样链接即可，接口零改动 |
| PlayerActivity.fetchLinesNative + httpGet + findField（原生取数层） | ≈130 | **原样复用并升格**为全 App 的取数范式（浏览层解析器照此模式写：HttpURLConnection + 桌面 UA + 正则/Jsoup） |
| PlayerActivity 的 WebView harvest 回退（startWebViewHarvest + HARVEST_JS + Bridge） | ≈180 | **保留**（见 §4）。它藏在 PlayerActivity 内部，与 MainActivity 的 WebView 无关，去浏览层 WebView 不影响它 |
| SharedPreferences 续播（`resume_{videoId}`/`lastline_{videoId}`） | 含在 PlayerActivity 内 | **原样**（本来就是原生存储，见 §3） |
| MainActivity（WebView 容器、CF 校验重试、广告拦截、菜单键逻辑） | 428 | 大半删除；保留极小一部分（CF 探针思路、键位约定）迁入新壳。广告拦截在原生侧天然不需要（没有页面 JS 去触发点击劫持） |
| tv.js（空间导航、焦点记忆、海报自救） | 273 | **删除**。焦点改由 Android 原生焦点框架 + RecyclerView 承担；海报自救逻辑（约 20 行规则）搬进原生图片加载 |
| tv.css（深色 6 列、焦点框、底栏瘦身等全部视觉适配） | 196 | **删除**。视觉改为原生布局一次写对，不再与站点 CSS 叠加博弈 |
| AssetsInterceptor + vendor/（bootstrap/zepto/video.js/字体等 9 文件，852KB） | 58 + 资源 | **删除**（其中 video.min.js 独占 562KB）。原生 UI 不加载任何站点前端资源 |
| libVLC AAR 合并构建（build-manual.sh 的 vlc-res 合入 + org.videolan.R） | 构建链 | 不变 |

一句话：**要新写的只有「浏览层」**——5 个页面解析器 + 原生列表/搜索/首页 UI + 图片加载，估算新增 1200–1600 行；删除约 750 行与站点前端纠缠的代码。

构建约束（影响选型）：现构建是手工链（aapt2+javac+d8，无 Gradle），依赖只能手工 vendoring jar（libVLC classes.jar 有先例）。因此：
- HTML 解析用 **Jsoup 单 jar**（约 450KB，可直接进手工链），不引入 OkHttp（其 okio/kotlin-stdlib 依赖链对工链是负担）——网络层沿用已验证的 HttpURLConnection 即可。
- 图片加载**不建议** Glide/Picasso（多 jar + 注解处理与手工链不合），自研轻量版：按显示宽（约 110 CSS px）降采样解码 + 内存 LRU + 磁盘缓存，约 150–200 行，海报这种单一场景足够。

## 3. 历史与续播：脱离 localStorage 的存储方案

先分清两个东西，现状完全不同：

| 数据 | 现状 | 原生化影响 |
|---|---|---|
| **续播进度**（看到第几集、哪条线、多少毫秒） | **已是原生**：PlayerActivity 用 SharedPreferences 按 `resume_{videoId}` = `集\|线\|毫秒` 存，另存 `lastline_{videoId}` | **零迁移、零改动** |
| **「看过」列表**（底部栏第五栏） | 站点 localStorage `playHistory`：play_new.js 在站内播放时写入 `[{videoId, lineId, title, name(集名), date(毫秒)}]`，按 videoId 去重、最新在前、**上限 10 条**、**无海报、无进度**；/history.html 纯前端读它渲染 | 需原生接管（下述） |

**原生方案**：
- 存储：一个 JSON 文件或 SharedPreferences 存 `List<HistoryEntry>`，字段与站点格式对齐再扩展：`{videoId, title, posterUrl, epName, lineIdx, posMs, updatedAt}`——posterUrl 与 posMs 从我们自己的播放流程里顺手记（PlayerActivity 的 onHarvestJson 有标题、saveState 有集/线/进度，写入点现成），上限放宽到 50 条。
- 写入时机：每次进入 PlayerActivity 成功取数后 upsert 一条；进度继续走现有 resume 键，两套数据各管一摊、互不污染。
- 「看过」页：原生网格复用模板 A 的卡片 UI 渲染本地列表，点任意一条直达 PlayerActivity（续播逻辑自动接上）。比站点版强：有海报、有进度、条数多。

**老数据迁移**：盒子现有 WebView 的 localStorage 里有至多 10 条观看记录。
- 方案：阶段一带一个**一次性迁移桥**——隐藏 WebView 加载 /history.html 或任意站内页，evaluateJavascript 读 `localStorage.getItem('playHistory')` 导出 JSON，映射为原生条目（videoId/title/name/date 直接对应；lineId 是站点线路 id、与原生线路序号不保证一致，迁移时只保留集名、线路回落默认；无海报——可按 videoId 逐个补抓 /play/ 页或搜索页的海报，≤10 条一次性成本可忽略，也可不补、列表先显标题占位）。迁移完成后打标记，不再重复导入。成本约半天含验证。
- 若判定不值得：不迁移的损失上限就是 10 条无海报的历史，「看过」会从空开始、看一两部即重建。**建议做迁移**，用户对「昨天看的那部还在列表里」是有感知的，成本又低。

## 4. 风险面

### 4.1 Cloudflare 对原生 HTTP 客户端的态度

**已有证据（不是推测）**：
- 2026-11-03 探测：curl + 桌面 UA 串行访问 `/`、`/hot/`、`/search`、`/play/`、`/api/getResN`（无 cookie）全部 200、多为 CDN HIT——curl 的 TLS 指纹与任何浏览器都不同，照样放行，说明当时 CF 未对该站启用严格的指纹/JS 挑战策略。
- 2026-11-04 复验：同样方式首页、播放页 200，播放页无「Just a moment」。
- v2.6.4 真机：fetchLinesNative 用 **HttpURLConnection**（Android 原生栈、非浏览器指纹）+ 桌面 UA 已实际跑通播放页与 API 两跳。
- 反例定位：此前老 WebView 在 /play/ 撞校验，是「wv 标记的老 UA + 老内核指纹」的组合问题；换桌面 UA 后 WebView 亦放行。即 CF 的闸主要看 UA/行为评分一类信号，不是「非浏览器一律拦」。

**残余风险与对策**：
- CF 策略是站点侧可随时收紧的（Bot Fight Mode、速率限制、按 ASN/IP 段）。原生客户端**没有执行 JS 挑战的能力**，一旦站点开启真人验证，原生直连会整体失效——这是原生化最大的单点风险，现套壳方案靠 WebView 尚有一战。
- 缓解组合（建议全部保留）：①请求节制——原生每进一个页面只发 1 个 HTML 请求 + 海报图（CDN 缓存），比 WebView 一次十几请求更不像机器人；串行、低频、不并发轰炸；②UA 与现方案一致的桌面 Chrome 串；③**双通道兜底**：PlayerActivity 内的 WebView harvest 保留（播放取数已有此机制，-401/CF 页时自动回退，v2.6.4 已实装）；浏览层解析失败或拿到校验页时，降级打开保留的 WebView「原站模式」入口（阶段一就留好，见 §6）；④getResN 与 HTML 都有 CDN 缓存，正常使用下请求量很小。

### 4.2 站点改版冲击：原生解析 vs 现注入

| 冲击面 | 现注入方案 | 原生解析方案 |
|---|---|---|
| 依赖点 | 站点 DOM 结构 **＋ 站点 JS 行为**（common.js 的懒加载/点击逻辑、v_tks 全局变量、play_new.js 的页面结构）＋ 站点 CSS 与 tv.css 的叠加关系 | 仅服务端 HTML 模板的 class/字段 ＋ token 算法 |
| 历史事故 | common.js 用了 `??` 新语法 → 老内核整文件失效、海报全空白，要靠 tv.js 自救复刻；tv.css `.row .item` 宽度规则误伤同名锚点 → 整列压成细条；每次站点 CSS 微调都可能与注入样式打架 | 尚无（未上线）；可预见的只有选择器失效一类 |
| 失效形态 | 常是**静默劣化**（海报空白、焦点乱飞），不易察觉 | 解析出 0 条/字段缺失，是**可检测的硬失败**，能自动降级 + 日志定位 |
| 修复成本 | 要同时懂站点新 DOM 和注入层的相互作用，盲调（不能断点） | 改解析器里的选择器常量，本地拿新 HTML 样本即可回归 |
| 共同风险 | token 算法变更（两边都靠 harvest 回退兜底）；站点关停/换域名（两边同命） | 同左 |

结论：改版风险原生侧**更小且更可控**，前提是把「解析失败自动降级」做进第一版。

### 4.3 原生化后会失去什么（站点免费给的东西）

1. **新板块/新功能自动跟随**：站点首页加板块、改推荐位，套壳自动就有；原生要改代码发版才跟得上（板块解析是数据驱动的，加板块大概率零改动；全新页面类型则要新写）。
2. **片单文章内容**（/kanlist/、/article/）：站点的编辑选片文章，套壳里点进去就能看；原生不做解析就没有（可二期补，结构不难）。
3. **播放页信息区**：播放页 HTML 里除隐藏字段外还有影片信息卡（简介/演职员等，article_title 字段与信息区 DOM）——现套壳用户其实也看不到（点播直接跳原生播放器了），所以**实际无损失**；若将来想在选集前展示简介，原生需另行解析该区块（本次未细测其结构，列为二期核对项）。
4. **站内搜索的容错表现**：搜索结果由站点搜索引擎生成（简繁支持、别名匹配），原生只是换了个渲染壳，结果质量仍来自站点——**不损失**；但搜索页那句「建议使用中文搜索」一类站方提示、以及结果里的描述文本，要靠模板 B 一并解析才不丢。
5. **与站点行为的一致性**：如站点将来上登录/会员/个性化推荐，套壳天然继承，原生要逐项重做。当前站点无账号体系，此项为远期假设。

## 6. 迁移路径（分阶段，每阶段可独立发版）

**阶段一：浏览层原生化（约 3–5 天）——核心阶段**
- 取数层：`IkanApi`（HttpURLConnection + Jsoup）：模板 A/B 两个解析器 + 首页/hot/category/billboard/搜索五个页面方法；分页两种模式（页码构造 + 搜索游标跟随页内链接）；海报 URL 拼装规则照搬 tv.js。
- UI 层：原生首页（板块行 + 6 列网格）、列表页（滚动加载下一页）、榜单页、搜索页（输入框 + 模板 B 结果列表）、看过页（本地数据，见下）。焦点用 RecyclerView 原生焦点链，视觉沿用现深色 + 琥珀焦点框（tv.css 的设计值直接抄成原生样式）。
- 历史：PlayerActivity 取数成功后写原生历史（新字段集）；一次性迁移桥读走 WebView localStorage 的 playHistory（≤10 条）后打标记。
- 点播：列表点击拼 `/play/{id}` → 现有 PlayerActivity，**播放链路一行不改**。
- 兜底：保留现 MainActivity 作为「原站模式」隐藏入口（如设置里开关或菜单键长按）；原生解析返回 0 条目/校验页时自动提示并可一键切过去。
- 验收：首页/电影/剧集/榜单/搜索/看过六入口全原生跑通，点播与续播无回归。

**阶段二：体验对齐与可选内容（约 1–2 天）**
- 片单（kanlist/article）解析接入（若有使用需求再做，可砍）。
- 播放页信息区结构核对，如需简介/演职员，在选集面板或标题区展示。
- 解析失败率与 CF 命中日志的本地计数（logcat/文件），为阶段三决策取数。
- 细节打磨：原生侧空状态/错误页文案（沿用现口语化提示风格）、海报磁盘缓存预热等。

**阶段三：去兜底评估（约 0.5 天决策，实施另计）**
- 运行数周后看数据：解析失败 ≈0 且无 CF 拦截记录 → 可删原站模式入口与 AssetsInterceptor/vendor（再省 852KB 与一整套 WebView 浏览代码）；PlayerActivity 内的 WebView harvest **建议长期保留**——它是对 token 算法变更的唯一保险，成本只是约 180 行静态代码，不占运行时资源（不触发时不加载）。
- 若期间站点大改版：先切原站模式保使用，再修解析器——阶段一的兜底设计就是为此存在的。

**总计**：约 5–8 天（含真机验证轮次；传输/装机走 nest 中转后单轮约 1 分钟，不再构成瓶颈）。
